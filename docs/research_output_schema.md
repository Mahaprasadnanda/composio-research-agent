# Research Output Contract & Schema Specification

This specification establishes the strict data contract between the automated research pipeline, the Pydantic data models (`src/research_agent/models.py`), and downstream analytical tools.

Every record generated by the research agent must validate against the `AppResearchRecord` Pydantic model.

---

## 1. Schema Mapping & Field Definitions

### Seed Input (`SeedAppRecord`)

| Field | Type | Description | Mandatory? |
| :--- | :--- | :--- | :--- |
| `id` | `int` | Deterministic 1–100 identifier. | Yes |
| `name` | `str` | Official name of the SaaS application. | Yes |
| `category` | `OriginalCategory` (Enum) | One of 10 original category strings. | Yes |
| `website` | `str` | Valid canonical URL of the application. | Yes |
| `documentation_hint` | `str` | Direct hint URL to official docs or portal. | Yes |
| `research_status` | `ResearchStatus` (Enum) | Defaults to `"pending"`. | Yes |

## 3. Strict Evidence & Attestation Rules

1. **At Least One Verifiable URL:** Any record with `research_status == "completed"` must contain at least one valid URL in `evidence_urls`.
2. **Excerpt Grounding:** `evidence_excerpts` must contain direct, unedited quotations from the referenced URL. The agent must never synthesize artificial quotes.
3. **Structured `EvidenceItem` Support:** Whenever possible, populate `evidence_items` with:
   - `url`: Exact deep-link URL (e.g. `https://developer.zendesk.com/api-reference/ticketing/tickets/tickets/`).
   - `title`: Page header or section title.
   - `excerpt`: Contextual paragraph establishing the auth or tier requirement.
   - `retrieved_at`: UTC timestamp of the retrieval session.

## 4. Exception & Edge Case Handling Protocols

### Protocol A: Conflicting Documentation
When a SaaS provider publishes contradictory information (e.g., pricing page says "API included in all plans", but API reference says "Enterprise OAuth credentials required"):
1. Follow the **more restrictive technical requirement** for the `buildability_verdict`.
2. Set `confidence_level = ConfidenceLevel.LOW`.
3. Set `verification_status = VerificationStatus.FLAGGED_FOR_REVIEW`.
4. Document the exact contradiction in `uncertainty_notes` citing both URLs.

### Protocol B: Inaccessible or Paywalled Documentation
When developer documentation is behind a customer login (e.g. DealCloud, PitchBook, or internal enterprise portals):
1. Do not fabricate API capabilities.
2. Set `buildability_verdict = BuildabilityVerdict.BLOCKED` or `BuildabilityVerdict.CONDITIONALLY_BUILDABLE` depending on whether public purchase is possible.
3. Set `primary_blocker = PrimaryBlocker.CONTACT_SALES_REQUIRED` or `PrimaryBlocker.DOCUMENTATION_INCOMPLETE`.
4. Set `confidence_level = ConfidenceLevel.LOW`.
5. Clearly state in `blocker_details`: *"Developer documentation is inaccessible to non-customers without an active enterprise contract."*

### Protocol C: Experimental, Niche, or Unofficial Tools
For tools like `Mermaid CLI`, `Sherlock`, `devin`, or `YouTube Transcript`:
1. Distinguish open-source tools/libraries (e.g. Mermaid CLI, Sherlock) from multi-tenant SaaS APIs.
2. For open-source projects with local CLI/SDK interfaces, document the execution interface under `api_types = [ApiType.OTHER]` with `access_requirements = "Open source MIT/Apache CLI; no hosted API key required"`.
3. For closed experimental AI apps without public APIs (e.g. NotebookLM), mark `buildability_verdict = BuildabilityVerdict.BLOCKED` and `primary_blocker = PrimaryBlocker.NO_PUBLIC_API`.
